The name a form won’t let you type

A website can pass common automated accessibility checks and still refuse to accept your name. This is a tool that finds out whether it will — and a study of how often New Zealand government forms get it wrong.

Rukshan De SilvaMSE907 CapstoneMaster of Software Engineering

If you only read one paragraph

Every website that asks for your name has a hidden rule about what counts as a name. A programmer wrote that rule, usually based on the names they had in mind at the time. I built a program that reads those rules and reports the ones that would refuse a real person’s name — then I’m measuring how often it happens on New Zealand government websites.

What is the actual problem?

When you type your name into a website, something checks it before letting you continue. That check is a rule someone wrote. Here are three harmful examples:

Full name
Ngā̄ti…
rule: letters A–Z only
  • refused Māori — the macron over the ā isn’t an A–Z letter
  • refused Zoë — same reason
  • accepted Smith
Full name
O’Brien
rule: no punctuation — often added as “security”
  • refused O’Brien — the apostrophe is part of the name
  • refused Anne-Marie — so is the hyphen
Full name
O
rule: at least 2 characters
  • refused O — single-letter names are real and common in several countries

When your name breaks the rule, you have two options: give up on the service, or type something that isn’t your name. Most people do the second. That altered version then goes into the records — onto the account, the invoice, the appointment letter.

In New Zealand this lands hardest on te reo Māori. The macron — the bar over ā, ē, ī, ō, ū — is not decoration and not an accent you can politely drop. It marks a long vowel, and vowel length changes what a word means. Remove it and you can end up with a different word entirely. A form that strips macrons is not tidying up a name. It is changing it.

Why hasn’t anyone caught this already?

Two reasons, and they compound.

Accessibility checking asks a different question

There are established international rules for making websites usable by disabled people, and good automated tools that check them. But those tools ask: can someone using a screen reader find this box, understand what it wants, and fill it in?

They never ask: will this box accept the name you were actually given? There is no rule in the standard that says an input must accept the values people legitimately need to type. So a form can pass those checks and still refuse your name.

Normal testing doesn’t find it either

A tester types their own name to see if the form works. If their name fits the rule, the box looks fine. The fault only shows up for people whose names the tester never thought to try — which is exactly the population least likely to be in the room.

The result is a fault that is written down in plain sight in the website’s own code, and nobody is looking at it.

So what did you build?

A program called FormFair. You give it a web page’s code — the instructions the browser follows to draw the page — and it does four things:

  • Finds the box that’s asking for a person’s name
  • Finds the rule attached to that box
  • Works out exactly which characters that rule will and won’t allow
  • Reports anything that would exclude a real name — quoting the exact line of code, explaining the problem in plain English, and saying how to fix it

It runs entirely on your own machine. Nothing is sent anywhere, so a developer can run it on work that hasn’t been published yet.

The part I’m most pleased with

When the tool meets a rule too complicated to be certain about, it says “I can’t decide this one” instead of guessing. Those cases are counted and shown next to the findings.

That matters more than it sounds. If a tool quietly skips what it can’t handle, you read the silence as “nothing wrong here” — and that’s worse than no tool at all.

What’s the clever bit?

The obvious way to test a name box is to throw a list of difficult names at it and see which ones bounce. That approach is wrong, and it took me a while to see why.

Picture a box with two rules at once: letters A–Z only, and maximum three characters. Now throw the test names at it:

Full name
Māori
rule: letters A–Z only, maximum 3 characters
  • refused Māori — 5 characters
  • refused O’Brien — 7 characters
  • refused Smith — 5 characters

Everything was refused, so you conclude the box rejects macrons and apostrophes. But it doesn’t. It refused all three for being too long. The character problem and the length problem are two different faults with two different fixes, and testing with names has just blurred them together and pointed at the wrong one.

So my tool doesn’t try names. It reads the rule and works out its alphabet directly — asking “does this rule allow ā? does it allow an apostrophe?” one character at a time, separately from any question about length.

It’s the difference between trying keys in a lock to guess what fits, and reading the lock’s specification.

That method — not the list of faults — is the actual research contribution. The faults are things people already know are bad. Deciding them reliably, from the rule rather than from examples, is the new part.

Why existing tools can miss this

Three groups work close to this problem. Each has a specific reason their approach would not surface it.

The accessibility tool builders

They’re answering the can-you-perceive-and-operate-it question described above. Accepting your name was never in scope, so it’s not an oversight on their part — it’s a different problem.

The software-translation researchers

These are people who build tools to check whether an app works properly in other languages. Genuinely close to my problem. But their tools work by looking at the rendered picture of the page — they catch German text overflowing a button, or Arabic laid out left-to-right by mistake.

A rule saying “letters A–Z only” looks exactly the same in every language and breaks no layout at all. Comparing pictures of pages can never see it.

The standards bodies

Unicode and the W3C have written genuinely good guidance saying don’t do this to people’s names. But guidance is advice. It isn’t a test. Turning “be careful with names” into a specific check — with a severity, and a procedure a machine can run without human judgement — is the step I haven’t found already done. That translation is the work.

Said carefully

What I can honestly claim is that I haven’t found such a tool — not that none exists. My literature search isn’t finished; there are twelve papers I still need to read in full before I can put it more strongly than that. Saying it precisely is part of doing it properly.

Is it research, or is it just a tool?

Both, and the combination is deliberate rather than a hedge.

The tool is the thing I built. The research is the question “does it actually work?” — answered with measurements rather than a demo. Anyone can show a tool working on an example they chose themselves. That proves nothing.

There’s an established way of doing this, called Design Science Research: you build something to solve a real problem, then evaluate it rigorously, and the contribution is the thing plus what you learned from testing it. That’s the shape of this project.

So there are three outputs: a working tool anyone can download and use, an honest measurement of how accurate it is, and a figure for how common this problem is across the government forms I sample.

How do you know you’re not fooling yourself?

This is the question I’d most want to be asked, because the risk is obvious: I built the tool and I’m the one grading it. It would be very easy to keep adjusting things until the numbers looked good, without ever noticing I was doing it.

So before collecting any data at all, I locked down and timestamped four things:

  • The exact list of faults the tool looks for
  • The plan for how accuracy would be measured
  • The list of websites I’d sample from, and the order I’d visit them in
  • The precise version of the software

Then, when the data collection happens:

  • Two people go through the forms by hand and write down what they find, independently, without being shown what the tool says
  • A third person settles any disagreement between them
  • Their answers are sealed with a cryptographic seal before the tool is allowed to run
  • The tool gets exactly one attempt at that data

It’s the same principle as sealing the exam answers before the exam starts. If I had quietly tuned anything afterwards to improve my score, the seals and the timestamps would give it away.

Who’s actually going to use it?

  • Web developers — run it over a page before it goes live and get back a list of problems, each with the offending line and a suggested fix
  • Government digital teams — check the forms they already have in production
  • Accessibility auditors — a check they currently have no tool for
  • Other researchers — the measurement, and the method behind it

Not the general public. Someone whose name keeps getting rejected doesn’t need a tool — they need the form fixed. The tool is for the people who can fix it.

What does it deliberately not do?

Being clear about the limits is part of the work, not an apology for it.

  • It only reads rules written into the page itself. If a website does its checking on its own servers, out of sight, the tool cannot see that and doesn’t pretend to.
  • It never promises that a form will accept a given name. It reports what the code declares, which isn’t always the whole story.
  • It looks for five specific faults, not every possible way to mishandle a name. Five that are common, damaging, and reliably detectable.
  • It doesn’t fix anything. It tells you what’s wrong and how to fix it. A person makes the change.

Where is it up to right now?

  • Done The tool is built, tested, and published openly for anyone to inspect
  • Done The list of faults it checks, each traced to a published standard
  • Done The measurement plan, written and locked before any data exists
  • Done The sampling list of government agencies, archived and timestamped
  • Waiting Yoobee confirmation of the applicable ethics pathway — nothing gets collected until then
  • Not yet Collecting the forms and having them labelled by hand
  • Not yet Results — there are none, and there won’t be until the steps above are finished

If someone asks what you’ve found so far, the honest answer is nothing yet, by design. Everything is deliberately locked so the finding, when it comes, means something.

How did you come to be doing this?

Two things had to line up: a problem that genuinely matters, and one that can actually be finished in fifteen weeks.

On the first: New Zealand has an official language whose spelling depends on a mark that computers routinely throw away. Government websites here are already monitored for accessibility — so they’re being checked regularly, just for something else entirely. That makes the gap narrow, specific, and worth closing.

On the second: this fault is written down. You don’t have to run the website, or guess at how it behaves, or ask anyone. The rule is sitting there in the page’s code where a program can read it. That’s what makes it something you can check reliably and measure honestly — and a lot of good-sounding project ideas fail exactly that test.

If you need to say it out loud

Thirty seconds

“You know how some websites reject names containing a macron, apostrophe or hyphen? I built FormFair, a tool that reads the rules behind a name box and warns developers when those rules could reject a real person’s name. I’m then testing it on New Zealand government forms to measure how accurate the tool is and how often the problem occurs.”

Two minutes

“Every website that asks for your name has a hidden rule about what counts as one. It was written with certain names in mind — English letters only, no punctuation, at least two characters.”

“In New Zealand that’s a real problem, because the macron in te reo Māori changes what a word means. A form that strips it isn’t tidying your name, it’s changing it. And you end up either abandoning the service or typing a fake version of your own name into an official record.”

“The odd part is that the usual automated checks don’t look for it. They ask whether a screen reader can find the box — not whether the box will take your name. So a form can pass them and still refuse you.”

“So I built a tool that reads the rule in the page’s code and works out exactly which characters it allows, one character at a time. And because I built it myself, I locked down the whole measurement plan and sealed the answers before running it — so the result can’t just be me marking my own homework.”
